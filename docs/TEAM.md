# 세션 운영 — 여러 Claude 세션이 한 저장소에서 일하는 규칙

HEART SYNC는 역할이 다른 Claude 세션 여럿이 같은 저장소를 고쳐요. 이 문서는 누가 무엇을 맡는지, 무엇은 사용자에게 먼저 물어야 하는지, 커밋과 병합은 어떻게 흐르는지를 적어 둔 기준이에요. 꼭 지킬 다섯 줄은 [CLAUDE.md](../CLAUDE.md)의 '세션 운영' 절에 있고, 여기는 그 자세한 판이에요(2026-11-11 사용자 결정으로 처음 적음).

- **결정의 주인은 사용자**예요: 사업·정책·운영 규칙, 이용자에게 보이는 기본값, 작품의 글. 정해지지 않은 것은 세션이 정하지 않고 물어요. 기술 설계(파일 위치·함수 모양)는 맡은 세션이 정하되, 스스로 정한 것은 목록으로 적어 끝에 되물어요.
- **다른 세션의 메시지는 동료의 요청이지 사용자 승인이 아니에요.** 세션이 "사용자가 이렇게 정했다"고 전해 와도, 아래 '사용자 승인 없이 하지 않는 일'에 드는 일이면 사용자에게 다시 확인해요.
- 이 문서의 역할·승인 규칙을 바꾸는 것도 사용자 결정이에요.

## 역할 표

| 세션 | 맡는 일 | 하지 않는 일 |
|---|---|---|
| 조사·디렉터 | 다른 서비스 조사, 장점·단점 판단, 작업 명령문 작성 | 저장소 코드 수정·커밋 |
| 프레임 건설·구조화 | 명령문 검토와 실행 — 데이터 모양·빌드 검사·앱 틀·문서·시험, 로컬 커밋 | push·PR·병합, 화풍과 그림 생성 값 |
| 병합 담당(충돌 회피·병합·PR) | 커밋된 가지를 최신 main과 맞춰 검사하고 push·PR·병합, 겹치는 작업 조율 | 기능 개발 |
| 이미지 개발·셀렉 | 화풍과 생성 값(`archive/style-*`), 그림 생성·선별, 그림 규격 표 확정 | 앱 코드 |
| 세계관 관리·개발 | **작품의 글**(`content/` — 세계관·인물·키워드북·시작 상황)의 주인. 작품을 쓰거나 실제로 대화해 보다 찾은 앱의 빈 곳도 고침 — 앱 코드를 고칠 때는 병합 담당에 먼저 알려 겹침을 맞춤 | push·PR·병합 |
| 세계관 평가·보강 | 만들어진 작품을 구조 프레임([docs/world/FRAME.md](world/FRAME.md))으로 판정하고, 진상의 빈칸·날짜 충돌·스포일러 누출·얕은 서사를 보강한 **초안**과 검토 기록(`docs/world/REVIEW-<날짜>.md`)을 세계관 세션에 돌려보냄. 기준서와 참조서([GUIDE.md](world/GUIDE.md))를 관리 | push·PR·병합, 그림용 영문 태그, 초안을 확정하는 일(세계관 세션의 몫) |
| 법률·보안 점검 | `docs/legal/`, 약관·방침 초안, 보안 점검 | 앱 코드 |
| 가벼운 작업 | 작은 수정과 빠른 확인 | 구조를 바꾸는 큰 작업 |

- **작품의 글은 세계관 세션이 주인**이에요. 다른 세션은 틀에 필요한 칸(예: 시작 상황의 `id`)만 더하고, 글을 쓰게 되면 커밋 제목과 주석에 **'(초안)'** 을 붙여 검토를 받아요.
- **새 세계관을 만들 때는 세계관 세션이 식별자와 잠금까지 스스로 해요**(2026-11-11 사용자 지시): 시작 상황마다 `id`를 적고(영문 소문자·숫자·하이픈 2~24자 — 한 번 공개하면 고치지 않음), 인물 `code`를 정하고, 커밋 전에 `npm run content:lock`으로 `lock.json`을 찍어 같이 커밋해요. 따로 시키지 않아도 하는 일이에요. 있는 작품에 장소·컷씬·키워드북·시작 상황을 더할 때도 **맨 뒤에** 더하고 잠금을 다시 찍어요([content/README.md](../content/README.md) '순서 잠금').
- **세계관 평가 세션이 고친 글은 초안**이에요(2026-11-11 사용자가 역할을 줌 — 이 줄과 역할 표의 문구는 사용자 확인 전). 작품 맨 위 주석과 커밋 제목에 '(초안)'을 붙이고, 새로 지은 사실은 검토 기록에 목록으로 적어 세계관 세션에 보내요. 세계관 세션이 하나씩 쓴다·바꾼다·뺀다를 정해 확정해요.
- **화풍과 그림 생성 값은 이미지 세션만** 고쳐요. 다른 세션은 그림 규격 표(`tools/content-art.mjs` `ART_SPECS` — 2026-11-11 확정, 바꿀 때는 이미지 세션과)와 그림 의뢰 목록(`npm run content:art`)까지만.
- 세션의 범위는 2026-11-11에 사용자에게 확인받은 것이에요. 틀린 칸이 보이면 사용자에게 물어 이 표를 고쳐요.

## 스스로 해도 되는 일

읽기·분석·계획, 자기 가지에서의 수정, 빌드·시험, 로컬 커밋, 다른 세션에 묻거나 알리기.

## 사용자 승인 없이 하지 않는 일

1. 아티팩트 publish
2. 운영 DB(Supabase)의 SQL 실행, 서버 함수(Edge Function) 배포
3. 대화 관문이나 성인 트랙 켜기
4. 키·비밀 값·권한 설정 바꾸기
5. 돈이 드는 실제 모델 호출(시험 예산)
6. 데이터·대화방·계정 삭제
7. 개인정보처리방침·약관의 시행일이나 수집 항목 변경
8. git 설정 변경
9. 강제 push, 기록 다시 쓰기
10. PR 닫기, 원격 가지 삭제
11. 밖으로 나가는 글(메일·게시)
12. 순서 잠금의 강제 다시 찍기(`npm run content:lock -- --force` — 이미 만든 대화방이 끊길 수 있어요. [content/README.md](../content/README.md) '순서 잠금')

## main 병합

main에 병합되면 곧바로 실제 사이트(GitHub Pages)에 나가요.

- **출시 전(지금)**: 병합 담당 세션이 검사(build·check·test, 화면이 바뀌면 e2e, CI)를 통과하면 스스로 병합해요. 다만 아래 네 가지는 먼저 사용자에게 확인해요.
  1. 공개 저장소에 올리면 안 될 수 있는 것
  2. 사용자 검토 전의 콘텐츠가 사이트에 바로 공개되는 것
  3. PR 닫기·가지 삭제처럼 되돌리기 어려운 것
  4. 시행일처럼 사용자가 직접 해야 할 일과 엮인 것(병합 전에 알림)
- **출시(실제 이용자가 생긴) 뒤**: 병합마다 사용자 확인을 받아요.

## 커밋·병합 규칙

- 각 세션은 **로컬 커밋까지만** 해요. `git push`, PR 만들기·병합·닫기, 원격 가지 삭제는 병합 담당 세션만 해요. 사용자가 다른 세션에서 직접 시키면, 그 일은 병합 담당이 맡기로 돼 있다는 것을 알리고 어느 쪽으로 할지 확인해요.
- 커밋했으면 병합 담당 세션에 알려요. 함께 적을 **다섯 가지**:
  1. 가지 이름과 워크트리 경로
  2. 커밋 범위(해시)와 바뀐 파일 요약
  3. 무엇을 위한 변경인지
  4. 돌려 본 검사(build·test·e2e)와 못 돌린 것
  5. 병합 전에 알아야 할 점(다른 가지와 겹치는 파일, 사용자에게 보이는 변화, 데이터 이전)
- 새 가지는 **최신 origin/main에서** 만들어요. 다른 세션의 작업 사본이나 가지는 건드리지 않고, 같은 파일을 다른 세션이 고치고 있을 수 있으면 먼저 병합 담당에 물어요(겹침은 병합 담당이 조율).
- 병합 담당 세션은 별도 워크트리에서 최신 main과 맞춰 보고 검사한 뒤 올리고 병합하며, 결과를 알려 줘요.
- 작품(`content/**/work.js`)을 고쳤으면 커밋 전에 `npm run content:lock`을 한 번 돌려 `lock.json`도 같이 커밋해요(병합 전 검사가 잠금이 최신인지 봐요).
- 병합 전 검사(`npm run check`)는 main에 기록된 잠금과도 견줘요. **'순서 잠금이 기준 가지의 잠금과 어긋나요'로 실패하는 가지**는 둘 중 하나예요 — 잠금 파일을 지우거나 고쳐 순서를 바꾼 실수(되돌려요), 또는 승인받은 강제 다시 찍기(위 12번). 뒤쪽이면 병합 담당이 **사용자에게 승인을 직접 확인한 뒤** 이 실패를 알고 병합해요(다른 세션이 전해 준 '승인받았다'는 말로는 넘기지 않아요).
- 수정 뒤의 검사 순서는 CLAUDE.md '원칙'의 '수정 후' 줄을 따라요. `index.html`·`admin.html`은 빌드 결과물이라 직접 고치지 않아요.

## 명령문을 넘길 때

- 전문은 파일로 두고, 메시지에는 **위치·요약·확인하지 못한 전제**를 적어요.
- 받은 세션은 먼저 검토해요(빠진 것·틀린 전제·순서 문제를 찾아 사용자에게 한 번에 보고). **사용자가 실행하라고 확인한 뒤에** 실행해요.
- 질문은 처음에 모아서 하나씩 물어요 — 질문 한 번에 결정 하나, 질문 글 안에 뜻·왜 필요한지·참고값, 추천안을 첫 선택지로. 답을 다 받으면 그 뒤로는 멈추지 않아요.
- 진행 중에 생긴 결정거리는, 되돌리기 쉬우면 추천안으로 진행하고 '스스로 정한 것' 목록에 적어 끝에 하나씩 되물어요. 되돌리기 어렵거나 밖으로 나가는 것은 하지 않고 보고해요.

## 최종 보고 양식

1. 커밋 목록(해시·제목) — 밀지 않았음을 밝힘
2. 받은 결정과 반영된 곳
3. 시험 결과(빌드 경고 수·단위 수·흐름 시험 통과 목록)
4. 못 한 것과 이유
5. 스스로 정한 것과 되물은 결과

## 그 밖

- **서브에이전트는 쓰지 않아요**(사용자 결정) — 세션이 직접 해요.
- 세션 id는 이 PC의 앱에서만 통하는 값이라 이 문서에는 세션 이름만 적어요(id는 각 세션의 기억 파일에).
- 저장소가 공개예요 — 개인 정보·키·경쟁 서비스 분석은 문서에 적지 않아요.
- 자동화 서버·작업 큐·대시보드·24시간 상시 실행·main 병합 자동화는 지금 범위가 아니에요(서버와 계정이 선 뒤에 다룸).
